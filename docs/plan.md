# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- 프론트엔드는 React, 백엔드는 FastAPI로 분리하고 JSON API로 연결합니다.
- 실제 서비스 DB는 Supabase의 PostgreSQL이며 초기 개발·테스트는 SQLite3로 진행합니다.
- React에서 데이터베이스에 직접 접속하지 않습니다. 회원과 데이터 접근 권한은 FastAPI에서 검사합니다.
- Supabase Auth는 이번 결정에 포함되지 않습니다. 회원 기능은 FastAPI가 담당하는 구성을 기준으로 하고 인증 유지 방식은 Phase 0에서 정리합니다.
- 아래 구조의 SQLAlchemy(데이터 모델), Alembic(테이블 변경 관리), Vite(React 실행·빌드), pytest와 프론트엔드 테스트 도구는 구현 제안입니다. Phase 0에서 호환 버전과 구성을 확인합니다.
- SQLite3와 PostgreSQL의 차이를 숨기지 않습니다. Supabase에서 마이그레이션과 주요 기능을 다시 확인합니다.
- 실패 응답에는 사용자가 이해할 수 있는 안내를 담되 비밀번호, 연결 문자열, 내부 오류 정보는 노출하지 않습니다.

## 3. 예정된 프로젝트 구조

기존 네 폴더를 유지하고 화면과 API 서버의 역할을 나눕니다. 아래는 개발 시 만들 구조이며 지금 생성하지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ requirements.txt
│  ├─ alembic.ini
│  ├─ migrations/         # SQLite3와 PostgreSQL 테이블 변경 이력
│  ├─ app/
│  │  ├─ main.py          # FastAPI 시작점
│  │  ├─ core/            # 환경 설정, 보안, 공통 권한
│  │  ├─ db/              # DB 연결과 세션
│  │  ├─ accounts/        # 회원 모델·입력 규칙·API·처리 로직
│  │  ├─ records/         # 공부 기록, 할 일, 오류 기록
│  │  └─ community/       # 댓글, 좋아요, 신고·운영자 API
│  └─ tests/              # 모델·API·권한 테스트
├─ frontend/
│  ├─ package.json
│  ├─ package-lock.json
│  ├─ index.html
│  ├─ vite.config.js
│  └─ src/
│     ├─ main.jsx
│     ├─ App.jsx
│     ├─ api/             # FastAPI 요청과 오류 처리
│     ├─ pages/           # 회원·기록·공개·운영자 화면
│     ├─ components/      # 메뉴, 카드, 입력칸, 확인창
│     ├─ styles/          # 공통·화면별 CSS
│     └─ tests/           # 화면·사용자 동작 테스트
├─ database/
│  └─ buildlog.sqlite3    # 로컬 개발용, 자동 테스트 DB와 분리, Git 제외
└─ docs/
```

데이터 흐름은 `React → FastAPI → SQLite3 또는 Supabase PostgreSQL`입니다. 환경별 `DATABASE_URL`로 연결을 선택하되 데이터베이스별 드라이버와 설정도 준비합니다. 연결 문자열 변경만으로 호환성이 보장된다고 보지 않습니다.

프론트엔드 공개 설정은 `frontend/.env.example`, 서버 설정은 `backend/.env.example`에 항목과 안전한 예시만 기록합니다. 실제 값은 각 환경의 `.env` 또는 환경 변수에 둡니다. 프론트엔드의 `VITE_` 설정은 브라우저에 공개되는 값이므로 비밀번호나 서버 인증 키를 넣지 않습니다.

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서와 Python·Node.js·데이터베이스 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 범위와 제외 기능이 맞는지 확인합니다. 이메일 확인, 비밀번호 찾기, 할 일 마감일·중요도, 내 할 일 검색, 댓글 답글은 만들지 않습니다.
2. 오류를 생성할 때 미해결만 허용하는지, 기본 미해결이되 해결 방법과 함께 해결 상태를 선택할 수 있는지 확인합니다. spec의 두 설명을 임의로 확정하지 않습니다.
3. Python과 Node.js, npm의 설치 여부·버전·실행 경로를 읽기 전용 명령으로 확인합니다.
4. Python의 SQLite3 사용 가능 여부와 SQLite 버전을 확인합니다. 실제 DB 파일은 만들지 않습니다.
5. 공식 문서에서 호환되는 Python·FastAPI·React·Vite와 데이터베이스·테스트 도구 버전을 확인합니다.
6. React 실행 주소는 `http://127.0.0.1:5173`, FastAPI는 `http://127.0.0.1:8000`, 로컬 DB는 `database/buildlog.sqlite3`를 기본 제안으로 정리합니다. 포트 충돌도 확인합니다.
7. `DATABASE_URL`, `SECRET_KEY`, `CORS_ORIGINS`, `VITE_API_BASE_URL`의 역할과 예시를 문서화합니다. 인증 방식에 따라 필요한 설정 항목은 확정 후 보완합니다.
8. 로그인 유지 방식을 정리합니다. 토큰 또는 쿠키 선택에 따라 만료, 브라우저 저장, CORS, 쿠키 사용 시 CSRF 방어와 테스트 방식을 함께 설계합니다. 회원 데이터는 SQLite3와 PostgreSQL에서 같은 규칙을 사용합니다.
9. SQLite3 외래 키 검사, 시각·시간대 처리, 이메일·닉네임 중복 판정과 검색 비교 규칙을 정리하고 PostgreSQL에서도 같은 결과를 확인할 기준을 만듭니다. 문서에 없는 사용자 규칙은 필요한 경우 질문합니다.
10. Supabase 프로젝트와 연결 정보는 Phase 13 전에 준비하면 됩니다. Phase 0에서 프로젝트를 만들거나 접속 비밀번호를 요청하지 않습니다.
11. API·화면·통합 테스트 도구와 실행 명령을 문서에 기록할 준비를 합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 `docs/setup.md`
- 코드, 패키지, 데이터베이스는 아직 변경하지 않음

#### 확인 방법과 완료 조건

- 문서 충돌과 미정 사항을 정리하고 해당 작업 시작 전까지 해결합니다.
- 도구 확인 결과와 선택한 버전·주소·인증 구성을 공유합니다.
- 패키지 설치, 가상환경·DB 생성 없이 환경 확인만 수행합니다.
- 환경에 막히는 항목이 없고 사용자가 결과를 확인하면 Phase 1로 넘어갑니다.

### Phase 1. FastAPI와 React 프로젝트 뼈대 만들기

#### 목표

React 화면에서 FastAPI 서버에 요청을 보내 정상 응답을 확인합니다.

#### 작업

1. `backend/.venv`를 만들고 FastAPI, 실행 서버, 설정·테스트에 필요한 패키지의 버전을 `backend/requirements.txt`에 기록합니다.
2. `backend/app/main.py`와 공통 설정을 만들고 비밀 설정은 서버 환경 변수로 읽습니다.
3. `frontend`에 React와 Vite 프로젝트를 만들고 `package.json`과 잠금 파일로 버전을 기록합니다.
4. 기본 React 화면과 CSS를 만들고 상태 확인 API 응답을 화면에 표시합니다. 요청 실패 안내도 만듭니다.
5. React의 API 주소와 서버의 허용 출처를 분리합니다. Phase 0에서 정한 인증 방식에 맞게 CORS를 설정합니다.
6. SQLite3 경로와 PostgreSQL 연결을 선택할 설정 틀을 만들되, 이 Phase에서는 테이블 생성이나 마이그레이션을 실행하지 않습니다.
7. 서버와 프론트엔드에 각각 `.env.example`을 만듭니다. 데이터베이스 비밀번호와 서버 키는 프론트엔드에 넣지 않습니다.
8. `.gitignore`에 SQLite 데이터·관련 임시 파일, 테스트 DB, 빌드 결과와 생성 파일의 제외 규칙을 필요한 만큼 보완합니다. 마이그레이션과 패키지 잠금 파일은 기록 대상에 둡니다.
9. 백엔드와 프론트엔드 테스트 실행 틀을 준비합니다.

#### 예상 변경 파일

- `backend/requirements.txt`, `backend/app/main.py`, `backend/app/core/config.py`
- `backend/tests/test_health.py`, `backend/.env.example`
- `frontend/package.json`, `frontend/package-lock.json`, `frontend/vite.config.js`, `frontend/index.html`
- `frontend/src/main.jsx`, `frontend/src/App.jsx`, `frontend/src/api/client.js`, `frontend/src/styles/base.css`
- `frontend/src/tests/`, `frontend/.env.example`, `.gitignore`

#### 확인 방법과 완료 조건

- FastAPI와 React 개발 서버가 각각 실행됩니다.
- 브라우저에서 React 화면·CSS와 API 응답을 확인합니다.
- API 자동 테스트, 화면 테스트와 프론트엔드 빌드가 통과합니다.
- 비밀값이 프론트엔드 번들·응답에 노출되지 않습니다.
- 아직 실제 사용자 테이블이나 DB 파일을 만들지 않았습니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 목표

SQLite3에서 이메일로 식별하는 사용자 모델과 데이터베이스 변경 이력을 만듭니다. 같은 모델을 PostgreSQL에서도 사용할 수 있게 설계합니다.

#### 작업

1. SQLAlchemy 모델과 DB 세션, Alembic 마이그레이션을 구성합니다. SQLite3 테스트 연결에서도 외래 키 검사를 적용합니다.
2. 고유한 이메일, 고유한 닉네임, 비밀번호 해시와 운영자 구분을 가진 사용자 모델을 만듭니다. 일반 회원가입에서 운영자 권한을 지정할 수 없게 합니다.
3. 닉네임은 2~20자이며 한글·영문·숫자·밑줄만 허용합니다. 입력 정리 규칙을 서버 검증에 적용합니다.
4. 이메일과 닉네임 중복을 데이터베이스 제약으로도 차단합니다.
5. 검증된 비밀번호 해시 라이브러리를 사용합니다. 직접 암호화 알고리즘을 만들거나 원문을 저장하지 않습니다.
6. 첫 마이그레이션을 만들고 `database/buildlog.sqlite3`에 적용합니다.
7. 자동 테스트는 별도 SQLite3 DB를 사용하며 개발 데이터나 Supabase DB를 초기화하지 않도록 분리합니다.
8. PostgreSQL에 맞지 않는 SQLite 전용 SQL을 피하고 DB별 차이가 필요한 곳은 명시합니다.

#### 예상 변경 파일

- `backend/app/db/`, `backend/app/accounts/models.py`, `backend/app/accounts/schemas.py`
- `backend/app/core/security.py`, `backend/app/core/permissions.py`
- `backend/alembic.ini`, `backend/migrations/`, `backend/tests/test_users.py`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법과 완료 조건

- 서로 다른 회원을 저장하고 다시 읽을 수 있으며 이메일·닉네임 중복이 차단됩니다.
- 닉네임 길이와 허용 문자를 검사합니다.
- 비밀번호 원문이 저장되지 않고 정상 검증이 됩니다.
- 빈 DB에 마이그레이션 적용, 서버 재실행 후 데이터 유지, 테스트 DB 분리를 확인합니다.
- 사용자 모델 테스트가 통과하며 PostgreSQL 검증 항목이 정리되어 있습니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

1. 회원가입 API와 React 입력 폼·화면을 만듭니다.
2. 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
3. 회원가입 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
4. 성공하면 로그인 화면으로 이동합니다.
5. 로그인 API와 React 화면을 만들고 이메일로 로그인하게 합니다. Phase 0에서 정한 인증 유지·만료 처리를 연결합니다.
6. 로그인 실패 시 이메일은 유지하고 비밀번호만 지웁니다.
7. 로그인 성공 시 내 기록 홈 화면으로 이동합니다.

4. 처음 누르면 저장하고 다시 누르면 취소합니다.
5. 현재 사용자의 좋아요 상태와 전체 개수를 보여줍니다.
6. 좋아요 실패 시 이전 상태와 개수를 유지합니다.
7. 공개 할 일에는 좋아요 화면과 처리 경로를 제공하지 않습니다.
8. 기록이 비공개가 되면 좋아요는 유지하되 숨기고, 다시 공개하면 복원합니다.

### Phase 13. Supabase PostgreSQL 연결과 호환성 확인

#### 목표

SQLite3에서 개발한 기능을 실제 서비스용 Supabase PostgreSQL에서도 확인합니다. SQLite3 자동 테스트는 계속 유지합니다.

#### 시작 전에 필요한 준비

- 사용자가 Supabase 프로젝트를 준비하고 DB 연결 정보를 서버의 로컬 환경 변수에 설정합니다. 비밀번호를 채팅에 붙여 넣지 않습니다.
- 접속 방식은 실행 환경의 네트워크와 Supabase 공식 연결 안내를 확인해 정합니다. 연결에 맞는 PostgreSQL 드라이버와 암호화 연결 설정을 사용합니다.
- 마이그레이션·검증용으로 빈 개발/검증 DB를 사용합니다. 운영 데이터가 있는 DB를 자동 테스트로 초기화하지 않습니다.

#### 작업

1. `DATABASE_URL`로 PostgreSQL을 선택하고 서버에서 연결을 확인합니다. React API 주소와 사용자 동작은 바꾸지 않습니다.
2. Alembic 변경 이력을 빈 PostgreSQL DB에 적용합니다. SQLite3 호환 처리가 PostgreSQL에서도 맞는지 확인합니다.
3. 외래 키, 고유 조건, 댓글·좋아요·신고 대상 제약, 삭제 관계와 상태 조건을 확인합니다.
4. 이메일·닉네임 중복 판정, 한글과 영문 검색, 공개 오류의 해결 방법 검색, 날짜·시간대·정렬 결과를 비교합니다.
5. SQLite3와 PostgreSQL에서 회원·기록·댓글·좋아요·신고 API와 권한 테스트를 같은 기준으로 실행합니다. 동시 요청에서도 중복이 생기지 않는지 확인합니다.
6. Supabase의 브라우저용 Data API 등 별도 경로에서 앱의 비공개 테이블에 직접 접근하지 못하도록 스키마 노출, 역할 권한과 필요한 RLS 설정을 검토합니다. FastAPI에서 쓰는 DB 계정의 권한과 역할도 확인합니다.
7. DB 비밀번호·서버 키가 프론트엔드 코드, API 응답, 로그에 노출되지 않는지 확인합니다.
8. SQLite 테스트 데이터를 자동으로 실제 DB에 옮기지 않습니다. 기존 데이터 이전이 필요하면 별도 범위를 정합니다.
9. 테스트 DB 분리와 연결·마이그레이션·재실행 절차를 문서에 기록합니다.

#### 예상 변경 파일

- `backend/requirements.txt`, `backend/app/core/config.py`, `backend/app/db/`
- `backend/migrations/`, `backend/tests/`, `backend/.env.example`
- `docs/setup.md`, 필요한 데이터베이스 설정 안내 문서

#### 완료 조건

- Supabase에서 마이그레이션과 주요 기능·권한·중복 방지 테스트가 통과합니다.
- SQLite3와 PostgreSQL의 차이를 확인하고 필요한 처리를 반영했습니다.
- 일반 사용자가 API 또는 별도 데이터 접근 경로로 비공개 기록과 신고 내용을 읽을 수 없습니다.
- Supabase 검증 환경이 준비되지 않았다면 이 Phase는 미완료로 남깁니다.

## 6. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 결과와 확인 내용을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
6. 각 화면 Phase는 API 입력·응답·오류·권한 검사와 React 화면을 함께 연결합니다. 브라우저 입력 검사만으로 검증을 끝내지 않습니다.
7. Phase 8의 댓글·좋아요 보존 확인은 해당 기능이 생기는 Phase 9~10에서 추가 검증합니다. Phase 8에서는 존재하지 않는 기능의 테스트까지 통과했다고 표시하지 않습니다.
8. 데이터 구조만 다루는 Phase 2·4는 자동 테스트와 DB 조회·재실행 확인으로 검증하고, 사용자 화면이 생긴 단계에서 직접 화면 확인을 이어갑니다.
9. 시간대와 상태 시각은 명시적으로 처리하며 저장 실패 시 트랜잭션을 되돌려 기존 데이터를 유지합니다. React는 입력값과 이전 상태를 보존하고 API 오류를 안내합니다.
